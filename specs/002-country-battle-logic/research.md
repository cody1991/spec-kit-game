# Phase 0 Research – 国家攻占规则调整

本文件汇总了围绕「以国家为单位的攻占与展示」所做的关键技术决策、理由以及备选方案，作为后续设计与实现的约束输入。

## Topic 1: 占领单位从区域到国家

**Decision**  
仅支持以「国家 ID」作为游戏内攻占与展示的唯一占领单位：

- 玩家在任何 UI 中都不会再看到「东南亚」「北美」「中美」等区域级条目作为占领目标或归属单位。
- `RegionMapping` 与 `countryMapper` 仍可用于启动时从旧的区域配置映射到国家列表，但映射完成后，游戏状态与逻辑层统一使用 `countryId` 作为所有权键。
- 任何运行时的占领/易主事件都以单个 `countryId` 为粒度进行记录和处理。

**Rationale**  

- 与规格保持一致：规格明确要求“不要有东南亚，北美，中美这些集合概念。都用国家来表示”。
- 简化心智模型：玩家只需要理解「某个国家是哪个指挥官的」即可，不再被区域聚合概念干扰判断。
- 减少隐藏联动：当前 `regionMapping` 可以让一次区域级更新影响多个国家，容易出现“一次操作导致多个国家变更”的隐式效果，与“逐个国家攻占”的目标相违背。

**Alternatives considered**  

1. 保留 `regionId` 作为内部所有权键，UI 仅显示国家级信息  
   - 问题：逻辑层仍然需要区域→国家的映射，`updateTerritoryOwnership` 等函数容易继续接受区域 ID 并一次性更新多个国家；调试和回溯都会变复杂。  
   - 结论：放弃，过度耦合且违背“一个国家一个国家结算”的直觉。

2. 完全移除 `RegionMapping` 与相关工具  
   - 优点：彻底消除区域概念，边界更清晰。  
   - 问题：现有指挥官初始控制区域配置依赖 `RegionMapping` 做首轮映射，完全移除会导致大量数据重写和初始化逻辑改动。  
   - 结论：保留为启动期工具，但不再在运行时攻占逻辑中使用区域键。

## Topic 2: 攻占流程粒度（逐个国家）

**Decision**  

- 将 `updateTerritoryOwnership` 在运行时只接受并处理 `countryId`：
  - 初始地图与指挥官势力分布生成阶段可以仍利用区域→国家映射批量填充初始 `territoryStates`。
  - 一旦对局开始，所有攻占事件中传递的目标标识都必须是单一国家 ID，不允许通过区域 ID 触发批量更新。
- 在战斗/胜利系统（例如 `battleSystem`、`victorySystem`）中，攻占结果只返回单个国家的所有权变更事件，并将每个事件独立入日志与状态流。

**Rationale**  

- 直接满足“一个国家一个国家来进行进攻，而不是一次性全部占领”的需求。  
- 使战报与可观测数据更清晰：每条攻占事件都可以明确指出「谁在何时占领了哪个国家」，有利于调试和复盘。  
- 有利于后续扩展（例如针对单个国家的防御加成、特性效果），避免区域级别的黑盒加成。

**Alternatives considered**  

1. 在 UI 层限制一次只选一个国家，但底层仍接受区域  
   - 问题：底层逻辑仍然有机会通过别的入口被调用（脚本、AI、测试），难以保证所有入口都只传国家 ID。  
   - 结论：不上，必须在状态更新层防止区域级占领。

2. 保留区域级批量攻占作为“高级技能”  
   - 优点：可形成一类特殊玩法。  
   - 问题：与当前规格目标冲突，且会极大放大平衡和表现复杂度；在历史世界征服这种题材下，也更推荐逐步推进而不是瞬间横扫整个区域。  
   - 结论：不在本版本引入，如未来确需此类玩法，应单独规格化并通过明确的 UI 入口区分。

## Topic 3: 占领后姓名展示与去重

**Decision**  

- 将每个国家的“当前占领者姓名/标识”视为 `territoryStates` 中单一字段的投影，由 UI 只读该状态：
  - 在状态更新时，旧占领者信息只会保留在 `previousOwnerId` 等非展示字段中，不再有任何地方维护“叠加展示”的文本节点列表。
  - 世界地图与各类面板仅通过 `countryId → TerritoryState` 的单向映射确定要展示的名字，每次渲染前根据最新状态进行覆盖，而不是在画布上累加文本。
- 在需要渲染姓名的地方，采用稳定的 `key`/标识与明确的销毁或重用机制，确保旧的文本对象被移除或复用，而不会留在屏幕上。

**Rationale**  

- 显示上“只保留一个名字”的本质是“单一来源的真相（SSOT）”：只要 UI 完全依赖状态模型，而状态模型只允许一个占领者，就不会产生重叠。  
- 从 `store.ts` 的实现来看，`territoryStates` 已经为每个国家维护了所有权与时间戳等信息；基于这一点统一展示逻辑可以减少状态分散。  
- 在 Phaser 场景与 React UI 之间建立清晰的边界：Phaser 专注于地图形状与颜色，React UI / overlay 专注于文字与面板，避免两者同时创建文本导致重复。

**Alternatives considered**  

1. 通过检测文本重叠进行“碰撞消解”  
   - 思路：允许临时存在多个姓名对象，渲染后再检查重叠并移除旧对象。  
   - 问题：实现复杂且脆弱，增加运行时开销，且很难完全避免边缘情况。  
   - 结论：放弃，问题应在状态层解决而不是在渲染后纠偏。

2. 使用图层分离 + 手工清屠除名图层  
   - 思路：占领后先清空姓名图层，再重绘所有姓名。  
   - 问题：对于国家数量较多的地图，频繁全量重绘成本较高；也无法从根本上解决状态不一致的问题。  
   - 结论：可作为极端 fallback，但主路径仍应依赖状态驱动的增量更新。

## Topic 4: 性能与可观测性

**Decision**  

- 性能策略：
  - 在 `scenes/world` 现有的渲染与 `PerformanceMonitor` 辅助工具基础上，对“国家攻占事件”相关的渲染路径重点关注，避免在每次攻占时对所有国家进行全表扫描或重算颜色。  
  - 使用基于 `Map<string, TerritoryState>` 的 O(1) 访问模式，对单个国家进行增量更新，而不是遍历整个列表。  
  - 如果发现性能退化超过既定阈值（例如交互 p95 延迟增加 >5%），在同一迭代内进行优化或记录明确的豁免说明与后续修复计划。
- 可观测性策略：
  - 在 `services/telemetry` 或相近模块中，记录关键的“国家所有权变更”信号，包含时间戳、国家 ID、前后占领者 ID 等。  
  - 对出现异常的展示情况（例如检测到某国家在短时间内被多次覆盖但地图上呈现异常状态）输出诊断日志，以便通过日志和遥测快速复盘问题。

**Rationale**  

- 本特性主要是在现有世界地图基础上调整规则与展示，不应引入新的性能瓶颈；利用现有的 `PerformanceMonitor` 和 Telemetry 可以降低额外实现成本。  
- 通过日志与指标将“国家易主”纳入可观测范围，可以在上线后快速确认是否存在连续占领导致的异常链式反应。

**Alternatives considered**  

1. 在每次攻占时完全重算整张地图的颜色与标签  
   - 优点：实现简单，逻辑上不易出错。  
   - 问题：对于数百个国家的地图，这种做法成本较高；在低端设备上容易造成卡顿。  
   - 结论：不采用，倾向于增量更新。

2. 不增加任何新遥测，仅保留现有日志  
   - 优点：实现成本最低。  
   - 问题：一旦出现“占领结果不符合规格”的 bug，很难从现有日志中快速排查；无法满足宪法中对可观测性和上线后 24h 内可复盘的要求。  
   - 结论：不可接受，需要必要的最小遥测。

## Topic 5: 测试策略

**Decision**  

- 使用 Vitest + Testing Library 作为主要单元/集成测试工具：
  - 为 `core/state/store` 中的 `updateTerritoryOwnership`、`updateTerritory` 等函数增加针对“区域 ID 不再触发批量占领”的单元测试和状态变更测试。  
  - 为 `countryMapper` 等工具增加针对地区→国家映射的回归用例，保证初始化仍能正确映射，但运行时不会误用区域键。  
  - 为与地图展示相关的 React 组件（国家详情面板、战报时间线等）增加测试，确保仅展示当前占领者姓名。
- 使用 Playwright 编写端到端测试：
  - 覆盖从开始界面进入世界地图、选择国家、发起攻占、查看结果的完整路径。  
  - 包含多次易主场景，确认每次刷新或重新进入对局时地图展示与最新占领状态一致。
- 为新逻辑设定覆盖率目标：新增代码路径的单元测试覆盖率不低于 90%，核心用户故事对应的 E2E 场景在 CI 中作为阻断门禁。

**Rationale**  

- 通过“测试即规范”的方式，将规格中的关键规则（国家粒度、禁止批量占领、姓名唯一展示）固化在测试中，避免后续改动回退。  
- Vitest 与 Playwright 已在项目中使用，复用现有工具能降低维护成本，并与当前 CI 流水线保持一致。

**Alternatives considered**  

1. 仅依赖手工测试和肉眼检查地图  
   - 问题：难以覆盖多轮攻占、多局对战等复杂场景；容易在后续迭代中回归。  
   - 结论：不符合宪法“测试即规范”的原则。

2. 引入额外测试框架（例如 Cypress）  
   - 优点：提供更多测试选项。  
   - 问题：增加技术栈复杂度，与现有测试体系重复；本特性并不需要额外框架即可覆盖需要的场景。  
   - 结论：保持 Vitest + Playwright 组合即可。
